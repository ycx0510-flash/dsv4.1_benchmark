# 一、带宽对时延的影响

## 1. ds41 总体

`带宽配对变化` sheet 的配对统计：

| 对比 | n | 中位变化 | 均值变化 | 变快 case 占比 |
| --- | ---: | ---: | ---: | ---: |
| 1T → 1.6T | 750 | -3.21% | -4.28% | 82.4% |
| 1T → 2T | 750 | -3.21% | -4.55% | 80.0% |
| 1.6T → 2T | 750 | -0.74% | -0.17% | 55.6% |
| 1T → 4T | 721 | -10.35% | -15.66% | 75.0% |
| 2T → 4T | 721 | -1.28% | -11.32% | 56.3% |

结论：

- **1T → 1.6T/2T 有收益，但只有约 3% 的中位改善。**
- **1.6T 和 2T 基本没有差异**（-0.74%，且只有 55.6% 的 case 变快），不能认为 2T 一定优于 1.6T。
- 4T 的 -10.35% 看起来更大，但 4T 是 HcPre/profiling 口径，不能直接当作纯 forward 的带宽收益。

> 注意：以上是全量样本的宏观数字，**不能直接推广到每个策略/每种计算量**。例如全量 1.6T→2T 中位 -0.74%，但 CP1 是 -3.32%、CP2 是 +1.77%；按 Q 拆开后差别更大。完整的分层和分布见第四节，最终结论以第 8 节的决策矩阵为准。

## 2. 重点对比：1T → 1.6T、1.6T → 4T、1T → 4T

为了只看这三个区间，统一取 **ds41 4T 有效且非错误的 721 个配对样本**：

| 对比 | n | 中位变化 | 均值变化 | p10 | p90 | 变快占比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1T → 1.6T | 721 | **-2.99%** | -4.18% | -11.06% | +2.04% | 82.1% |
| 1.6T → 4T | 721 | **-3.31%** | -11.73% | -46.84% | +7.62% | 64.9% |
| 1T → 4T | 721 | **-10.35%** | -15.66% | -47.95% | +5.63% | 75.0% |

分策略：

| 策略 | 1T→1.6T | 1.6T→4T | 1T→4T |
| --- | ---: | ---: | ---: |
| DP8CP1EP8 | -1.15% | -3.06% | -10.02% |
| DP4CP2EP8 | -8.63% | -5.19% | -15.18% |
| DP2CP4EP8 | -2.20% | -1.71% | -10.49% |

可以怎么解读：

- **1T → 1.6T 的中位收益约 3%，且 82% 的 case 变快，收益比较一致。**
- **1.6T → 4T 的中位收益也只有约 3.3%**，但分布很宽（p10=-46.8%，p90=+7.6%），说明部分 case 有明显收益、部分没有；不是全场景收益。
- **1T → 4T 的 -10.35% 主要来自少数收益很大的 case 和 4T 的口径差异**；不能简单理解为“4T 相对 1.6T 还能再降 10%”。
- 1.6T → 2T 仅为 **-0.40%**，进一步说明 1.6T 之后继续增加带宽的边际收益很小。

**工程结论：**

> 从现有数据看，1T → 1.6T 有约 3% 的稳定收益；1.6T 之后再往上加带宽，1.6T→2T 基本无收益，1.6T→4T 的中位收益也只有约 3%，因此“**1.6T 后继续增加带宽收益不大，不必为此上 4T**”是合理的工程判断。

但必须保留一个口径限制：**4T 是 HcPre/profiling 派生时间，不是 1T/1.6T/2T 同口径的 no-prof timing**。要做严格的“1.6T vs 4T”带宽结论，应该补一组 ds41 4T 的 no-prof 测量，或 DeepInfer 在同口径下跑 1.6T 和 4T。

## 6. 小Q长KV专题

### 6.1 子集定义

这里把“小Q长KV”定义为：

- **长 KV**：`context_length >= 131072`
- **小 Q**：`pdt <= 2048`

其中 ds41 的 `pdt = round((1-hit) * L) + 140`，是每 die 实际要算的 query token 数，已经包含 YOCO replay 的 140 token 尾。不是单纯的 `(1-hit)*L`，也不是 128 对齐后的 cache 长度。

子集共 **91 个 case**：

| 策略 | case 数 | pdt 中位 | L 取值 |
| --- | ---: | ---: | --- |
| DP8CP1EP8 | 21 | 1058 | 128K / 256K / 512K / 1M |
| DP4CP2EP8 | 31 | 725 | 同上 |
| DP2CP4EP8 | 39 | 559 | 同上 |
| **合计** | **91** | **690** | 128K 32 / 256K 28 / 512K 20 / 1M 11 |

特征：命中率集中在 **0.95–0.999**，L 越长，要达到小 Q 所需命中率越高（1M 的 11 个 case 命中率均 ≥0.993）。这 91 个 case 的 ds41 4T 数据全部有效，DeepInfer 也 **91/91 全部 OK**。

### 6.2 全部带宽对比：1T / 1.6T / 2T / 4T

先看同口径的 1T/1.6T/2T。下表单位 ms；“变快占比”指配对变化小于 0 的 case 占比。

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **ALL** | 91 | 287.99 | 284.33 | 283.89 | **-1.52%** | 83.5% | **+0.44%** | **36.3%** | -1.16% |

| DP4CP2EP8 | 31 | 292.30 | 286.37 | 293.23 | -1.99% | 96.8% | +2.42% | 0.0% | +0.42% |
| DP2CP4EP8 | 39 | 291.93 | 287.75 | 287.79 | -1.55% | 94.9% | +0.11% | 43.6% | -1.72% |

直接结论：

- **1T → 1.6T 有收益，但中位只有 -1.52%**；主要是 CP2/CP4 的约 -2%，CP1 基本没有收益（+0.14%）。
- **1.6T → 2T 中位 +0.44%，只有 36.3% 的 case 变快；CP2 甚至中位变慢 +2.42%。**
- 因此在这个子集里，**整体 1.6T 已经饱和，继续上 2T 没有可复现收益**；但分策略看 CP1 的 1.6T→2T 是 -2.94%，CP2 是 +2.42%，不能把整体结论套到每个策略。更系统的策略/计算量交叉见第四节。

按 L 拆开，同时看 4T：

4T 加进来后，有三个很关键的现象：

1. **128K–512K 的 raw 4T 看起来很漂亮**：1.6T→4T 中位约 -43.7% 到 -46.4%，CP2 的 31 个 case 全部是 4T 更快（0/31 慢于 2T）。
2. **到 1M 直接翻转**：1.6T→4T 中位变成 **+5.73%**，2T→4T 变成 **+5.27%**，11 个 case 里有 6 个 4T 慢于 2T。翻转主要来自 1M/CP4：该组 7 个 case 的 4T 是 283–326 ms，而同一批 case 的 1T/1.6T/2T 约 282–317 ms；CP1/CP2 的 1M 点 4T 仍然明显更快（CP1 118 vs 244 ms，CP2 167 vs 287 ms）。
3. **CP1 128K 也不稳定**：1.6T→4T 中位只有 -25.93%，10 个里有 3 个 4T 慢于 2T；CP1 在其他 L 才回到约 -51% 到 -54%。

所以“4T 加进来”后的结果不是“4T 全面更快”，而是：**4T 的 raw 降幅在 CP2 和 128K–512K 很显著，但在 CP1 128K 变弱、在 CP4 1M 直接反转。** 再加上 4T 本身就是 HcPre/80 口径，这 44%–47% 不能直接当作带宽收益。

L 越长，1T→1.6T 的收益确实有上升趋势：128K/256K 约 -1.2%，1M 到 -5.53%。但注意 1M 只有 11 个点（CP1 1 / CP2 3 / CP4 7），这个数字只能作为趋势，不能当作稳定收益。**无论哪一档 L，1.6T→2T 都基本为 0，最长上下文也没有再收益。**

阈值敏感性（`小Q长KV阈值` sheet）也支持这个结论：把 `L_min` 从 64K 扫到 1M、`pdt_max` 从 1024 扫到 4096，共 15 组阈值，**1.6T→2T 的中位变化始终在 +0.09% 到 +0.71% 之间，没有一组为负收益**；1T→1.6T 则从 -1.34% 到 -5.55%，随 L 增长而增加。4T 的 raw 比值也随阈值和 L 大幅波动，不能形成稳定的带宽趋势。

### 6.3 为什么小Q长KV对带宽不敏感

在同一策略内比较 L 从 128K 增到 1M 的 1T 时延：

| 策略 | 128K | 1M | 8×L 的时延增长 |
| --- | ---: | ---: | ---: |
| DP8CP1EP8 | 161.64 | 247.16 | +52.9% |
| DP4CP2EP8 | 267.43 | 304.70 | +13.9% |
| DP2CP4EP8 | 290.82 | 309.18 | +6.3% |

CP2/CP4 把 KV 切到多卡后，L 放大 8 倍，时延只增加 6%–14%，说明每 forward 的固定开销/调度/通信占主导，KV 扫描不是主项。CP1 虽然增长 53%，但它的 1T→1.6T 中位是 +0.14%，说明这部分增长也不是“HBM 带宽不够”能解释的；否则 1.6T 应该带来明显改善。

再粗算 `pdt × L`（query 数 × KV 长度，近似 KV 扫描工作量）：128K→1M 时，CP1 / CP2 / CP4 的粗略工作量分别增加约 **11× / 17× / 26×**（因为 pdt 中位数也从 860/529/330 涨到 1189/1119/1084），但 1T 时延只增加 **53% / 14% / 6%**。如果是 KV 扫描主导，时延不可能这么平；这进一步说明这个子集主要是固定开销在托底，带宽只影响其中很小一部分。

用 4T 表里的设备侧三分诊断也能看到（这是 4T HcPre 窗口内，不是 forward 同口径）：

| 范围 | computing | comm | free |
| --- | ---: | ---: | ---: |
| ALL | 40.67% | 0.96% | **58.25%** |
| 131072 | 35.13% | 0.91% | 63.78% |
| 262144 | 39.50% | 1.00% | 59.90% |
| 524288 | 43.77% | 1.04% | 55.14% |
| 1048576 | 46.56% | 0.94% | 52.50% |

comm 占比不到 1.1%，不是通信受限；free/idle 一直在 52%–64%，即使 1M 也超过一半。这个形态不支持“继续加 HBM 带宽会有大幅收益”。

### 6.4 4T 加进来后怎么读：大降幅不是稳定带宽收益

把 4T 加进来后，raw 数字确实很吸引眼球：

- ALL：4T 中位 153.24 ms，1T→4T -46.10%，1.6T→4T -44.59%，2T→4T -46.16%。
- CP2：31/31 个 case 的 4T 都快于 1T/1.6T/2T，1.6T→4T 中位 -44.59%。
- 128K–512K：1.6T→4T 中位约 -43.7% 到 -46.4%。

但把 L 和 CP 拆开后，4T 并不是稳定收益：

1. **1M 翻转**：1.6T→4T 中位 **+5.73%**，2T→4T **+5.27%**，11 个 case 中 6 个 4T 慢于 2T。翻转主要来自 1M/CP4：7 个 case 的 4T 是 283–326 ms，而同 case 的 1T/1.6T/2T 约 282–317 ms。
2. **CP1 128K 变弱**：1.6T→4T 中位只有 -25.93%，10 个里有 3 个 4T 慢于 2T；CP1 在其他 L 才回到约 -51% 到 -54%。
3. **整体也有反例**：91 个 case 中，15 个的 4T 慢于 1.6T，17 个的 4T 慢于 2T。如果 4T 的 44% 是带宽收益，不应出现这种分布。

更重要的是口径：1T/1.6T/2T 是 ds41 **no-prof forward timing**；4T 是 `HcPre window / n_hcpre` 派生值，是 **kernel/HcPre 窗口口径**，不是端到端 forward 同口径。1M/CP4 还出现 4T（283–326 ms）高于同 case 1T/1.6T/2T（282–317 ms）、而 DeepInfer 只有 193–198 ms 的反超，这证明 4T 列不能直接当带宽收益使用。

用理想化加法模型反推：若 `T = 固定部分 + KV带宽部分`，1T→2T 的 -1.16% 意味着 KV 带宽部分最多约占 2.3%；1M 子集的 -5.07% 对应最多约 10%。即使把 1.6T→4T 的 2.5× 带宽全部折算，端到端理论上界也只有约 1.4%（全子集）/ 6%（1M 子集），远小于 44%。**所以 4T 的 44%–47% 主要是 HcPre 口径与 4T 数据异常，不是稳定的带宽收益。**

结论：**把 4T 加进来后，能确认的是“4T 在部分 CP2/中短 L 上 HcPre 口径更快”，不能确认“4T 对端到端有约 45% 的带宽收益”。** 小Q长KV 的可比数据仍然支持 1.6T 后饱和；要证明 4T 真实收益，必须补同口径的 no-prof 4T 测量。

### 6.5 DeepInfer 对比

这 91 个 case DeepInfer **全部成功**，没有出现高 capacity 组的模型加载失败或 OOM：

| 指标 | 小Q长KV 子集 | 高 pdt 对照 |
| --- | ---: | ---: |
| DeepInfer OK | 91/91 | 249/315 |
| DeepInfer peak torch allocated 中位 | 48.39 GiB | 53.77 GiB |
| DeepInfer minimum device free 中位 | 16.70 GiB | 9.44 GiB |

原因不是“长 KV 更省内存”，而是这些小Q case 的 **per-die new token 小，capacity band 低**，SymmBuffer/Engram/CP 工作区没有进入高 capacity 组；高 pdt 组才会撞到 53.56 GiB 级权重加工作区的 HBM 墙。

按 ds41 4T 与 DeepInfer 配对：

| 范围 | n | ds41 4T（HcPre） | DeepInfer | DI 相对 4T | DI 变快占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ALL | 91 | 153.24 | 145.51 | -0.81% | 54.9% |
| DP8CP1EP8 | 21 | 109.42 | 126.95 | +13.74% | 0.0% |
| DP4CP2EP8 | 31 | 155.37 | 147.90 | -4.80% | 67.7% |
| DP2CP4EP8 | 39 | 159.14 | 148.63 | -8.78% | 74.4% |

这里仍然要保留 4T 口径限制：DI 的 -0.81% 不能当成严格的“DI 比 ds41 快 0.81%”。分策略看，CP1 是 DI 明显慢（+13.74%，21 个 case 全部更慢），CP2/CP4 是 DI 更快。1M 子集里 ds41 4T 中位 283.58 ms、DI 195.22 ms（-30.35%），但该组 4T 本身有上面提到的异常，不能单独作为 DI 优势的证据。

### 6.6 小Q长KV结论

> **小Q长KV 不是单一大类：整体上 1T→1.6T 约 -1.52%、1.6T→2T +0.44%，但分策略是 CP1 -2.94%、CP2 +2.42%、CP4 +0.11%。结论只能写成：CP2/CP4 以 1.6T 为合理档位；CP1 的 2T 相对 1.6T 有收益（约 -6.3 ms），但相对 1T 只有 -1.4%（约 -2.2 ms），不足以推广成“小Q长KV 都要上 2T”。**
>
> 4T HcPre 列在 CP2 和 128K–512K 确实显示约 -44% 到 -47% 的大降幅，但 1M 翻转为 +5.73%、17/91 个 case 的 4T 慢于 2T、CP4 1M 有 6/7 反超，而且 4T 不是 no-prof 同口径。因此不能把这 44%–47% 当成稳定的端到端带宽收益；4T 设备侧 free 占比 52%–64%、comm <1.1%，也不支持“带宽瓶颈”判断。
>
> **工程判断：小Q长KV 先按 CP 和 Q 分桶；CP2/CP4 1.6T 足够，CP1 的 2T 只有小边际。若 4T 决策必须严格量化，先补 no-prof 4T 的同口径实验。**

# 三、为什么 ds41 看似都成功，DeepInfer 不成功

## 1. 状态总览

```text
DeepInfer:
  OK      684
  FAILED   46
  OOM      20

ds41:
  1T/1.6T/2T: 750/750, errors=0
  4T: 730 行有 forward, 20 行 no_trace, 9 行 errors>0
```

## 2. 46 个 FAILED：模型加载阶段失败

46 个 FAILED 全部落在 8 个 `ready_rank=0` 的高容量组，尚未进入 case：

| 策略 | capacity | 失败 case 数 |
| --- | ---: | ---: |
| DP8CP1EP8 | 59008 | 13 |
| DP8CP1EP8 | 104960 | 7 |
| DP4CP2EP8 | 118016 | 8 |
| DP4CP2EP8 | 209792 | 3 |
| DP2CP4EP8 | 59008 | 1 |
| DP2CP4EP8 | 118016 | 8 |
| DP2CP4EP8 | 236032 | 4 |
| DP2CP4EP8 | 419456 | 2 |

合计：13+7+8+3+1+8+4+2 = **46**。

典型错误：

- DP8CP1EP8 cap59008：
  - `Engram gather_sf` 申请 **2.86 GiB** 失败
  - 失败时 `57.48 GiB already allocated`，仅 1.54 GiB free
- DP8CP1EP8 cap104960：
  - `HcclChannelAcquire ... tcp connect fail`
  - 部分 rank 是 `SymmBuffer` 申请 **11.68 GB** 失败
- DP4CP2EP8 cap118016：
  - `HCOMM runtime exception ... empty pointer`
  - 部分 rank 是 `HrtRaGetAsyncReqResult ... error[328107]`
- DP4CP2EP8 cap209792：
  - `SymmBuffer` 申请 **11,672,748,032 B** 失败
- DP2CP4EP8 cap236032：
  - 申请 **9,672,065,024 B** 失败
- DP2CP4EP8 cap419456：
  - 申请 **11,668,553,728 B** 失败

这些错误都发生在：

```text
worker.load_model
-> allocate_userbuffer
-> Engram / CP / SymmBuffer
```

不是 case 执行完后的 reload 阶段。

## 3. 20 个 OOM：模型加载成功后，case 执行 OOM

| 策略 | capacity | OOM case 数 |
| --- | ---: | ---: |
| DP8CP1EP8 | 32768 | 6 |
| DP4CP2EP8 | 59008 | 13 |
| DP2CP4EP8 | 59008 | 1 |

合计 **20**。

典型例子 DP4CP2EP8 cap59008：

- 模型加载成功，`ready_rank_0..7` 全部存在
- 第一个 case 运行申请 **8.00 GiB** 失败
- launcher 杀掉整组，用剩余 case 重新 load 模型
- 每个 case 重复 OOM

日志中每次 reload 都重新 materialize 约 **53.56 GiB** 权重，说明模型加载本身是成功的，失败点是 case 的 cache/workspace 需要的内存。

## 4. group 次数与重复加载

计划：

```text
750 cases / 30 groups
```

实际：

```text
49 groups
```

多出 **19 次 model load**：

- DP8CP1EP8 cap32768 重复 6 次
- DP4CP2EP8 cap59008 重复 12 次
- DP2CP4EP8 cap59008 多 1 次

具体表现：

- DP4CP2EP8 cap59008：13 → 12 → … → 1 个 case，共 13 次尝试
- DP8CP1EP8 cap32768：22 → 17 → 12 → 10 → 8 → 4 → 1，共 7 次尝试

每次 reload 约 140 秒，重复 reload 会显著拉长总时间，并把 HCCL 的 `tcp connect fail` 等二次错误放大。

## 5. 是不是“rank 没释放又 load 模型”？

**不是主因，日志不支持这个判断。**

证据：

1. 20 个 case OOM 所在组都有完整的 `ready_rank_0..7`，说明模型加载和通信组初始化已经完成。
2. DP4CP2EP8 cap59008 每次重新加载模型都成功，随后第一个 case 在 8 GiB 分配处 OOM。
3. 46 个 FAILED 的组是 `ready=0`，失败发生在模型构造/Engram/SymmBuffer 分配，还没有进入 case。
4. 日志显示重新加载时权重重新 materialize 约 53.56 GiB，并没有“旧 rank 还占着模型导致新模型加载不了”的直接证据。

更准确的因果链：

```text
DeepInfer 完整模型内存占用高
+ 高 capacity band 的 SymmBuffer/Engram/CP 工作区
-> 模型加载阶段或首个 case 阶段 OOM
-> launcher 杀掉组并把剩余 case 重新加载
-> 重复 140s 级 model load
-> 进一步放大耗时和通信/HCCL 二次错误
```

## 6. 与 ds41_mini 的根因差异

ds41_mini 的 1M@0.97 修复文档显示：

- QLI `p_sum` 原来一次物化 `[T, L/ratio]`，约 30.86 GiB
- 改为按 q 行分块后，1M@0.97 cp1 峰值：
  - **71.69 GiB → 28.83 GiB**
- 同时使用合成权重/层间共享等更轻的 benchmark 结构

DeepInfer 当前：

- dummy 权重仍加载完整 40 层，日志约 **53.56 GiB materialize**
- 高 capacity 组再叠加 Engram/CP/SymmBuffer
- 所以相同 L/h 下，DeepInfer 先撞上 HBM 墙，而 ds41_mini 还能跑完

这不是“rank 未释放”一个点能解释的，核心是**模型/工作区内存预算不同**。

# 四、带宽多角度交叉分析：输入长度 × 实际计算量 × 并行策略

> 前面按全量中位数得到的“1.6T 后收益很小”只能算宏观结论。按策略、实际计算量和输入长度拆开后，**不同策略、不同工作量对应的最优带宽档位并不一样**。本节用配对分布、分位数、分层交叉和 205 个完全匹配的 `L/hit` 样本重新分析；4T 也放在同一套框架里对照，但始终保留口径标记。

## 1. 指标与统计方法

数据：

- ds41 750 个 case；1T/1.6T/2T 全部 750 个有效。
- ds41 4T：730 个有 forward，其中 9 个 `errors>0` 剔除，**721 个有效**；20 个 no_trace 不参与。
- 1T/1.6T/2T 是 no-prof forward timing；4T 是 `HcPre window / n_hcpre`，标为 `4T*`，不是同一口径。

计算量指标：

- `pdt`：ds41 每 die 的 query/replay token 数。它不是简单的 `(1-hit)*L`，还包含 replay 尾；同一 L/hit 下随 cp 近似反比。
- `R_global = pdt * cp`：整个请求的 query/replay token 总数。同一 L/hit 下不同 cp 的 R 近似相同，因此跨策略比较时用它描述真实待算 token 更合适。
- `attn_G = R_global * L / 1e9`：query 数 × context 长度的粗略代理，量级上代表 KV 扫描工作量，单位是 10^9 token-pair；不是严格 FLOPs，但用来分桶足够。

统计方式：

- 所有变化都是**逐 case 配对**计算 `b/a - 1` 和 `b-a`，不是拿两条边际中位数相除。
- 每张分层表都给出 `n`、`p10/p25/p50/p75/p90`、变快比例（变化 < 0 的 case 占比）和中位绝对时延变化 `median Δms`。
- 低 n 的格子会保留 n，避免把 1–3 个点当成规律。

为什么要强调配对：全量 4T 的边际中位数是 157.54 ms，2T 是 231.31 ms，直接相除会得到约 -31.9%；但逐 case 配对的 4T vs 2T 中位数只有 **-1.28%**，p25 = -34.46%、p75 = +2.59%。边际中位数之比没有配对意义，这正是不能只看一个中位数的原因。

## 5. 长度 × 计算量交互

完整 7×8×4 的 `L×Q` 明细在 Excel `L×Q分层`。核心现象：

- 固定 `Q=4097–8192`，L 从 8K 到 1M 的 1→1.6 中位约 **-8.4% 到 -11.5%**，1.6→2 约 **-2.8% 到 -3.5%**；L 变化只影响几个百分点。
- 固定 `Q<=512`，L 从 8K 到 512K 的 1→1.6 大多在 **-0.75% 到 -2.0%**；只有 1M 的少量极端点达到 -4.85%（n=1，不可靠）。
- 在 1M 内再按 Q 拆：`Q<=2048` 的 1→1.6 约 -5.5%（n=11）；`Q>=4097` 的 1→1.6 约 -8.3% 到 -9.3%，1→2 约 -10.8% 到 -11.9%。所以“1M 收益高”很大程度是 1M 样本里 Q 更大/更重，而不是纯 L。
- 1.6→2 的收益几乎只由 Q 决定：Q≤4096 基本为 0 或负收益，Q≥4097 才有约 -2.5% 到 -3.2% 的边际收益。

**结论：L 和 Q 有交互，但主效应是 Q；L 是二级修正。**

小Q长KV 的定义是 `L>=131072` 且 `pdt<=2048`，本身就是一个高命中、长 L、低 query 的 91 点切片。它里面 4T HcPre 恰好很小（中位 153.24 ms），而 2T 约 284 ms，所以 raw 4T 显示 -46%；但全量 4T vs 2T 只有 -1.28%，且有 43.7% 的 case 变慢。**不能把 91 个点的 -46% 当成全量 4T 收益。**

4. **Q>65536**：只有 7/3/2 个点，且 CP2/CP4 方向相反，**样本不足，不能下结论**。

并行策略：

- **CP2**：1→1.6T 最强（匹配样本 -9.01%），但 1.6→2T 中位 +1.52%，2T 不是它的收益点。
- **CP1**：1.6→2T 最强（-2.92%），总 1→2 也最好（-9.71%）；但轻 Q 时 1.6T 点非单调，不能把 2T 的改善全部归因于带宽。
- **CP4**：接近饱和（1→1.6 -2.17%，1.6→2 +0.30%），额外带宽收益最小。
- 这些是 matched 205 个 L/hit 的结果；不是“所有 L/hit 下 CP1 一定比 CP2 好”，但足以说明**策略和带宽必须一起选**。

4T（条件拐点，重点）：

- 全量 4T vs 2T 中位 **-1.28%** 是因为绝大多数 case 不在台阶内（721 个有效 case 中，台阶内只有 183 个，509 个是 no-gain）；台阶内这 183 个 case 的 2T→4T 中位是 **-46.7%**，绝对 **-129ms**，而同一批 case 的 1T→1.6T 只有 -1.9%、1.6→2T 只有 +1.3%。
- **短 L（≤16K）没有 4T 台阶**：2T→4T 中位 +0.8%，绝对 +1.4ms；端到端 1T→2T 也基本为 0。20–64K 整体 4T 也没有大台阶，但 CP2 在 20K/Q≤512 有局部早台阶（-35.9%，n=32），属于策略拐点差异。
- **长 L（约 ≥96K）+ 小 Q（高命中）** 才有台阶：1/1.6/2T 基本一条平线，4T 是唯一的大杠杆。
- 台阶边界随策略变化：**CP2 最早/最宽**（约 20K/Q≤512 起，256K/512K 可到 Q≤4096），**CP1 主要在 Q 1K–4K**，**CP4 最窄**（1M 只有 Q≤512）。这就是“规律相同、拐点不同”。
- 4T 仍是 HcPre/80 窗口口径，不是端到端 no-prof；作为选型依据需要确认可复现并补同口径 4T，但**条件规律本身是真实的**：短 L 无台阶、长 L+小 Q 有 4T 断崖。

**最终建议：**

> 先看 **L 和 Q 是否落在 4T 拐点区**，再看 1.6T/2T。短 L 或普通 Q：端到端 1T→2T 约 0–几 ms，4T 也没有台阶，不需要加档；中/重 Q 但不在 4T 台阶：优先 1.6T，2T 只有小边际；**长 L + 小 Q：1/1.6/2T 端点基本平，4T 是唯一显著台阶，应优先验证 4T 的可复现性，而不是把 2T 当过渡方案**。CP2 的 4T 窗口最早/最宽，CP1 需要更大的 Q，CP4 窗口最窄。


# 五、建议

1. **优先解决高 capacity 带的内存问题**
   - 把 CP1 cap59008/104960、CP2 cap118016/209792、CP4 cap236032/419456 继续拆细
   - 不要一开始把所有 case 放在一个高 capacity 组

2. **不要让 OOM 的容量带逐个 case 重载**
   - 同一个容量带连续 OOM 后设置熔断
   - 否则会出现 13 次 × 140 s 的重复模型加载

3. **试 DeepInfer 的 indexer 预算**
   ```bash
   export DEEPINFER_INDEX_ATTN_MEMORY_LIMIT=$((2*1024*1024*1024))
   ```
   这对应 ds41 的 2 GiB QLI streaming 预算；它能降低 indexer 峰值，但不能解决 53.56 GiB 权重和 SymmBuffer 容量问题。

4. **组间增加清理/回落等待**
   - 可以降低快速 reload 导致的 HCCL tcp connect/HCOMM 二次失败
   - 但不会解决模型/工作区本身的内存不足

5. **对比口径先统一**
   - 要严格比较 forward 时延，应使用双方 no-prof timing、相同 iterations/warmup、相同 replay/hit 几何
   - 4T 的 HcPre window 数据只适合做趋势/分解，不适合直接和 DeepInfer timing 做绝对排名
